# Wrap Tehreer Core in Tehreer-ReactNative

The repo is `/Users/mta/Learning/Tehreer-ReactNative` (GitHub `Tehreer/Tehreer-ReactNative`, npm package `tehreer-react-native`, TypeScript, strict). It exposes every public header of Core to React Native through one **C++ JSI layer shared by iOS and Android** and a TypeScript API shaped like Tehreer-Web, Tehreer-Android and Tehreer-Cocoa. Text is drawn by thin native views (Android `Canvas`, iOS `CGContext`); there is no Skia and no WebAssembly. Core is a git submodule at `Libraries/TehreerCore` and is built as the unity build (`Source/Tehreer.c`).

The first spike (issue #3) verified the TurboModule registration, the Core build on both platforms and the version call on the iOS simulator and an Android emulator; those statements below are stated as facts. Where this skill still says **(spike)**, the statement is the intended design, not a verified fact; update the skill when the issue that builds it settles it.

## 1. Principles

1. **Core owns the logic.** Layout, shaping, matching, drawing math, run backgrounds and decorations, cluster and caret math, typeface registry and style matching live in Core. The wrapper never re-implements them. If React Native needs a rule Core lacks, add it to Core (with tests there), then bridge it.
2. **The bridge is thin.** A binding converts arguments, calls one `TR*` function, converts the result. No algorithms, no mirrored state, except what section 6 allows.
3. **TypeScript keeps React Native and web-style terminology, mirroring the Web wrapper.** `Rect {x, y, width, height}`, `Color` as `0xAARRGGBB`, `fromIndex`/`toIndex`, `typeSize`, `strokeRadius`. Core words are mirrored when they say something new. Defaults are Core's. Where Web, Android and Cocoa already agree on a name, use it.
4. **API compatibility is not sacred.** Break the API when that lets the wrapper follow Core more directly; say so in the summary.
5. **Native-only concerns stay in the wrapper:** painting draw callbacks (Android `Canvas`, iOS `CGContext`), Fabric views and measurement, font loading from files and assets, finalizers.
6. **No dependency without asking.** The library has no runtime npm dependency beyond `react` and `react-native` as peers. Dev dependencies are kept minimal. Ask before adding a package, a CocoaPod, a Gradle dependency, or downloading anything.
7. **New architecture only.** Fabric and C++ TurboModules, Hermes. No old bridge, no `NativeModules`.
8. **No Skia.** Not as a dependency, not as an optional one.

One class per file, file named after the class (PascalCase). Everything under `internal/`, `cpp/generated/` and `NativeFunctions.ts` is never public API.

## 3. Bindings

- **Generated.** `scripts/generate-bindings.mjs` (adapted from Tehreer-Web) parses `Libraries/TehreerCore/Headers/Tehreer/*.h` and, for each public function, writes a C++ JSI binding and a typed declaration in `NativeFunctions.ts` with the C signature in a comment. The classic SheenBidi API of the `unicode` package is not generated: `cpp/runtime/SheenBidiBindings.cpp` binds it by hand because SheenBidi keeps pointers into the string (see `scripts/README.md`, SheenBidi), and `scripts/generate-unicode-enums.mjs` writes its enumerations. Declared-but-undefined functions go in an `EXCLUDED` set (`TRVersionGetString`, `TRTextGetSheenBidiText`, as in Web). The generator has node tests; a header change that the generator cannot express fails loudly instead of being skipped.
- **Installation (verified).** One C++ TurboModule (`NativeTehreer`, class `facebook::react::TehreerModule`, `cpp/TehreerModule.*`) installs `global.__tehreer` (defined with `Object.defineProperty` through JSI: read-only, non-configurable, non-enumerable), once, from `initialize()`. The value is a plain object that holds all bindings and is frozen (`Object.freeze`), so no function can be replaced; it is not a `HostObject` because `generated::InstallBindings(rt, target)` fills an object and a `HostObject` cannot keep `jsi::Function`s safely across runtime teardown. The module has one codegen method, `install(): boolean`, which receives the `jsi::Runtime&`; everything else is called on the object. Calls are synchronous JSI calls; nothing is serialized and nothing crosses the old bridge. `cpp/runtime/TehreerBindings.cpp` installs the generated bindings plus `getVersion`, `smokeTest`, `disposeHandle`, `isHandleDisposed`, `isHandleMutable` and `handleEquals`; debug builds (no `NDEBUG`) add `testCreateProbe`, `testGetProbeReleaseCount` and `testCollectGarbage` for the device tests (the callback hooks are listed in `tests/device/CallbackTests.ts`).
- **How a library registers a C++ TurboModule (verified on RN 0.88.0).**
  - `package.json` `codegenConfig`: `name` (here `TehreerSpec`, which names the generated `TehreerSpecJSI.h`), `type: "modules"`, `jsSrcsDir: "src/specs"`, `android.javaPackageName`, and `ios.modules.<ModuleName>.className`. There is no `cxxModule*` key in `codegenConfig`: the Android keys live in `react-native.config.cjs`. The spec file must be named `Native*.ts` and must `export default TurboModuleRegistry.get<Spec>("Name")` (the one allowed default export; the lint rule is disabled on that line). `get`, not `getEnforcing`, so importing the library never throws when the module is not linked; `initialize()` throws instead. Codegen produces `Native<Name>CxxSpec<T>`; the module derives from it with CRTP.
  - **iOS:** `ios.modules` maps the module name to an Objective-C++ class (`TehreerModuleProvider`) that conforms to `RCTModuleProvider` and returns `std::make_shared<TehreerModule>(params.jsInvoker)` from `getTurboModule:`. Codegen writes it into `RCTModuleProviders.mm` in the app's `ReactAppDependencyProvider`; no AppDelegate change.
  - **Android:** `react-native.config.cjs` (CommonJS, because `package.json` is `"type": "module"`) sets `dependency.platforms.android.cxxModuleCMakeListsPath` (relative to `android/`), `cxxModuleCMakeListsModuleName` (the CMake target) and `cxxModuleHeaderName` (the header **and** class name: the generated `autolinking.cpp` does `#include <TehreerModule.h>` and `std::make_shared<TehreerModule>(jsInvoker)` inside `facebook::react`, so the class must live in that namespace and have a static `kModuleName`). The app's CMake project adds `android/CMakeLists.txt` as a subdirectory and links the target into `libappmodules.so` with the plain `target_link_libraries` signature (mixing in the keyword signature fails). The CLI drops an Android library that has an `android/` folder with `build.gradle` or a manifest but no `ReactPackage` class, so `android/` has a `TehreerPackage` (it registers no module) and a `build.gradle` that applies `com.facebook.react` for the codegen; without those files the library would be a "pure C++ dependency" instead.
- **Core in each platform (verified).** Android: `android/CMakeLists.txt` does `add_subdirectory(Libraries/TehreerCore)` with `TR_DEPS_DIR=Libraries/Dependencies` (so nothing is fetched by Gradle) and `TR_CONFIG_UNITY=ON`, after switching off FreeType's optional zlib, bzip2, png and harfbuzz lookups. iOS: `tehreer-react-native.podspec` compiles `Tehreer.c` plus FreeType, libunibreak, SheenBidi (unity) and `harfbuzz.cc` from `Libraries/Dependencies` directly into the pod, with the file lists of tehreerCocoa's `Package.swift`; see section 12 for the pitfalls. The podspec lives at the package root because CLI autolinking only globs `*.podspec` there and CocoaPods rejects `source_files` outside the pod root. `scripts/fetch-deps` must run before `pod install` and before the Gradle build (the podspec fails with a message if it did not).
- **Example app resolution.** `example/` depends on `file:..` and Metro runs the library from `src/`: `example/metro.config.js` watches the root, blocks the root `node_modules` (a second React Native breaks the app), maps `tehreer-react-native` to `src/index.ts` and maps the `.js` suffix of relative imports in `src/` to `.ts` (Metro does not do that itself).
- **Off-device JSI tests (tried once, not reproducible from the repo).** A throwaway program linked `cpp/runtime/TehreerBindings.cpp`, Core and its dependencies against the macOS slice of `hermesvm.framework` (from the hermes-engine pod, with `destroot/include`), created a Hermes runtime and printed `1.0.0 true` for `__tehreer.getVersion()` and `smokeTest()`. That harness is not in the repo. What is: `tests/handlerTable.test.ts` compiles `tests/fixtures/handler-harness/Harness.cpp` with `cpp/runtime/HandlerTable.cpp` and `Callbacks.cpp` against the declarations-plus-counters stub in `tests/fixtures/jsi-stub` (no engine, no Hermes) and runs it: who destroys a handler and on which thread, the queue, no lock held while an error is made, the callback error slot and `BeginCall`. Everything that needs a real engine is still device-only; the other node tests only pin names that C++, TypeScript and the configs share (`tests/native-module.test.ts`).
- **(spike) Open: the packed npm library cannot build.** `Libraries/Dependencies` (FreeType, HarfBuzz, libunibreak, SheenBidi) is fetched by `scripts/fetch-deps` and is not in `files`, and nothing downloads it for a consumer, so a package installed from npm lacks the sources that both the podspec and `android/CMakeLists.txt` compile. Only the repo checkout (and the example app) builds today. A follow-up issue decides how consumers get them; no download is added to the build meanwhile.
- **iOS builds (verified for #5).** The pod builds the example app without errors for `generic/platform=iOS` (arm64), `generic/platform=iOS Simulator` with `ARCHS=arm64`, `ARCHS=x86_64` and `ARCHS="arm64 x86_64"` (a fat `libtehreer-react-native.a`); the x86_64 harfbuzz failure of the spike did not reproduce. The xcodebuild log shows `-x c` with `-std=c89` for Core, `-std=gnu99` for FreeType, SheenBidi and libunibreak, and `-x c++` with no per-file `-std` for `harfbuzz.cc` and the wrapper (C++20 comes from `CLANG_CXX_LANGUAGE_STANDARD`); the wrapper sources (`cpp/`, `ios/`) produce no warnings, Core and the dependencies do. `use_frameworks! :linkage => :dynamic` needs the third-party headers as `project_header_files` (otherwise the framework copies Core's and SheenBidi's same-named headers and fails with "Multiple commands produce"), and then compiles, but the framework link fails until the marshalling functions that the generated bindings declare (`FromHandle`, `FromNumber`, `ToStringView` and others, runtime issue #7) are defined.
- **Not verified:** release builds, reload and Fast Refresh, `use_frameworks!` linking (see above), the contents of the packed npm package, and Android API levels other than 28 (the Medium_Phone_R emulator did not fit on disk).
- **Hermes.** Use only JSI APIs that Hermes supports. No `eval`, no reliance on a WebAssembly runtime.
- **ABI.** The binding calls Core's C functions natively, so structs by value and returned structs follow the platform C ABI (no WASM `ret` pointer tricks). Floats are `float`; JS numbers are doubles; convert at the binding.

## 4. Handles, lifetimes, ownership

- A wrapper extends `NativeObject` and owns **one** Core reference. The JSI side keeps the `TR*Ref` in a `HostObject`; the finalizer releases the reference if `dispose()` was never called. Nothing may depend on the finalizer running. `dispose()` is idempotent; `nativeHandle` throws "already disposed" afterwards. `equals(other)` compares handles.
- **Follow Core's ownership rule.** `Create`/`Copy` returns an owned reference: wrap it with `adopting`. `Get` is not retained by Core: the generated binding calls `TR*Retain` itself before it makes the handle, so what it returns is owned too and is wrapped with `adopting` as well. `retaining(handle, retain)` is only for a handle the caller already holds and keeps: it calls the `TR*Retain` binding and adopts the new handle. Never `retaining` the result of a `Get` binding; that leaks a reference. A child therefore never depends on its parent staying alive. The exception is data behind a pointer (section 5), which belongs to its owner and is only valid while the owner lives; the wrapper keeps the owner alive.
- **How it is built (verified on iOS, Hermes).** `cpp/runtime/HandleObject.*` is the `HostObject` of a handle: one reference, a `TR*Release` thunk taken from `HandleTraits`, idempotent `Dispose()`, and a destructor that only calls the thunk. A handle remembers its `kGroup` and `kMutable`; `ToHandle<Ref>` throws "already disposed", "is not a Tehreer handle", a group mismatch or "is immutable". `FromHandle` releases the reference if it cannot wrap it. Hand-written functions take handles through `AsHandleObject` (a `dynamic_pointer_cast`, since other libraries install host objects too). The generated code only declares the `marshal` templates, so `MarshalHandles.cpp` and `MarshalValues.cpp` instantiate them from explicit lists, checked by `tests/runtime.test.ts`. Indices and counts (`TRUInteger`) go through `ToIndex`/`FromIndex` (-1 is `TRInvalidIndex`), never through `ToNumber<T>`: on 32-bit targets `TRUInteger` and `TRColor` are one C type. Typed arrays and `DataView`s are read through getters captured from the engine's prototypes at install (`bindings.intrinsics`), so app-defined getters and Proxy traps never run during a conversion. In TypeScript `NativeObject<Kind>` (`src/internal/NativeObject.ts`) holds the `Handle`, `adopting`/`retaining` are its statics, `dispose()` calls `disposeHandle`, and `equals` calls `handleEquals`, because two handles of one Core object are different JavaScript objects.
- **Internal constructors** use the `adopt` token overload, marked `/** @internal */`. Public constructors create the Core object and throw if creation fails.
- When Core takes an object (typeface, replacement, font features, glyph cache, typesetter) it retains it. A temporary made only for the call is disposed after it. `LineLocator` is the exception: Core does not retain the frame, so the wrapper keeps the frame and the renderer.
- Core objects are immutable and thread safe after creation; `Renderer`, `ShapingEngine`, `FrameResolver` and `TMutableText` are mutable configuration objects. Hermes runs JS on one thread, but views may draw on another: never change a mutable object while something is drawing or shaping with it.
- **Callbacks (built for #9; not yet run on Hermes).** Function pointers handed to Core are static C++ trampolines created once. `userData` is a key into the handler table, never a pointer to a JS value. Only `TRReplacementCreate` keeps JavaScript after the call (check `MANUAL` in `scripts/generator/config.mjs`: glyph-image native data stays native), and it is bound by hand in `cpp/runtime/ReplacementBindings.cpp`. The draw callbacks of the native painters stay native; the ones of the JS drawing surface (`cpp/runtime/DrawBindings.cpp`, section 9) put a handler in the table only between `installDrawContext` and `restoreDrawContext`.
  - **Table.** `cpp/runtime/HandlerTable.*` is one table for the process (a trampoline gets only the key), each entry knowing its runtime and thread. Keys are never 0. `Remove` runs on any thread (the last release of a replacement can, and an engine finalizer can run it on the JS thread during a collection) and touches no JS: **the handler is always queued**, never destroyed inside `Remove`, and the runtime's thread destroys it at the next `Drain`. `Drain` costs one atomic read when the queue is empty, and runs on every binding (`marshal::RethrowCallbackError` calls `DrainRetiredHandlers`), in `disposeHandle`, `Add` and `Find`, so a handler never waits for the next replacement to be made. `Find` finds nothing on another thread, since a JSI runtime is not thread safe. `Add` throws its `JSError` after it released the table's lock (making an error can collect garbage and run a finalizer that calls `Remove`).
  - **Trampolines.** `runtime::InvokeHandler(userData, body)` (`Callbacks.h`) is what every trampoline is made of, and every trampoline is `noexcept`: it catches everything, records the first error in a thread-local (the thread of the runtime), does not run the handler again during that Core call, and returns false so the trampoline can fill in a zero result and set `stop` where Core offers it (`TRReplacementCallbacks.computeRoom` has none, so a failure leaves the room zero and later rooms are zero too). Core calling from another thread gets a zero room and no handler call (nothing could receive an error there); that means a replacement is only measured on the JS thread, which the Fabric measure path must keep in mind.
  - **Stale errors.** Every binding starts with `marshal::BeginCall()`, which forgets an error that was recorded but never thrown (a Core call that did not end in a rethrow), so it cannot surface from an unrelated call. Nothing legitimate is lost: after a handler failed no handler runs again during that Core call, so no binding can start between the failure and its rethrow. Hand-written bindings that call Core do the same.
  - **Rethrow.** Every generated binding calls `marshal::RethrowCallbackError(rt)` right after its Core call (one thread-local read) and throws the very value the handler threw. A binding that returns a reference it owns calls `RethrowCallbackError(rt, result)`, which releases it first. Anything that can reach a handler (shaping and laying out text with a replacement) is covered this way, hand-written bindings must do the same.
  - **Ownership.** The handler belongs to the replacement, not to its handle: Core calls `finalize` when the last reference goes, which drops the entry, so disposing a handle that Core still holds (a text attribute) keeps the handler. On `NULL` from Core, `TRReplacementCreate` removes the entry itself. Enumerations that only collect use `marshal::Collector` on the stack instead (no table).
  - **Teardown.** The `lifetime` host object on the frozen `__tehreer` is reachable until the engine shuts down; its destructor ends every entry of the runtime. JSI allows destroying `jsi::Object`s from a host object destructor and forbids it after the runtime, so this is the one place; the table itself is leaked on purpose. Entries removed later are not found, and a trampoline then finds no handler.
  - **Known limit.** A handler runs JavaScript while Core holds a buffer pointer of the same call (`TRTypesetterCreateTruncationToken` reads `tokenString`), so a handler that detaches that buffer could break the "no JavaScript while a pointer is held" rule of section 3; nothing guards it yet. The same holds for the handles of `defaultAttributes` in `TRTypesetterCreate`, which are borrowed (not retained) while the `computeRoom` handlers run, so a handler must not dispose a typeface or replacement that only the default attributes reference.

## 5. Memory: structs, views and lists

- **Structs** that are read or written are described once in the C++ runtime with the C struct's name, and each description is checked at compile time against the real layout with `static_assert(sizeof(...))` and `offsetof`. The TypeScript side has no struct offsets: the binding returns objects or typed arrays. Add a struct description, never read an offset by hand in the generated glue. **How (verified by node tests, device suite for #8):** the generator prints `cpp/generated/Layouts.h` from the parsed headers for every struct and union (a mirror declaration plus `static_assert`s on size, alignment, member types and offsets); by-value structs get codecs in `Structs.h` and an entry in `kStructCodecs`; `cpp/runtime/StructCodecs.cpp` adds `TRAttribute` (`{ type, value }`, the union member picked from `type`) and `FindStructCodec`; debug builds expose `testRoundTripStruct(name, value)` and `testGetStructNames()`, used by `tests/device/StructTests.ts`. The mirror is a check of what the header says, not of the compiler's whole layout: it cannot see tail padding (a member added after the last one that fits in the padding changes no offset and no size), a union member smaller than the biggest, or a member whose typedef changed (the scalar typedefs are checked on their own: `TEHREER_CHECK_SCALAR` asserts that `TRFloat`, `TRUInt16`, `TRGlyphID`, ... are still the fundamental type the header names, with its width). Structs that hold function pointers (`TRDrawCallbacks`, `TRPathCallbacks`, `TRReplacementCallbacks`) have their layout checked but no JS conversion. The read-only lists of a typeface (`TRVariationAxis`, `TRNamedStyle`, `TRPaletteEntry`, `TRPredefinedPalette`, `TRBitmapStrike`, built for #15) have read-only codecs in `cpp/runtime/StructCodecs.cpp`: `FindStructCodec` finds them (`readPointerStructs` converts them), `StructCodecNames`/`testRoundTripStruct` do not (they cannot be written), and the strings and arrays they point to (names, coordinates, colors) are copied into the object, so an element read is a snapshot that points into no Core memory.
- **Lists (built for #10; node tests pass over a fake of the native functions, the device suite is written but has not run on a device).** `src/collections/` has `List` (abstract, with `NumberList` and `PointList` as interfaces, names and members as Tehreer-Web: `length`, `get`, `at`, `slice`, `isEmpty`, `toArray`, `forEach`, `map`, `reduce`, `find`, `findIndex`, `some`, `every`, iteration), `NumberKind` (Web's five kinds: `UInt8`, `UInt16`, `Int32`, `UInt32`, `Float`), `CoreList`, `IndexedList` and `CoreMemory`; `List`, `NumberList`, `PointList` and the kinds are exported from `src/index.ts`, the rest is `@internal`. A list reads Core memory when an element is asked for, keeps its owner and fails with "already disposed" once the owner is; `IndexedList` makes objects from an index. Constructors read nothing and call nothing native (`CoreMemory` keeps the `PointerView` and the count).
  - **PointerView is a host object** (`cpp/runtime/PointerViews.*`): address, element name, element size, **element count** and the owner's `HandleObject`. JavaScript can read `element`, `elementSize` and `count` and nothing else, and cannot make one, so native code that is given a view trusts it (a forged `{ address }` object is refused). The count is what the count function of Core paired with the getter said when the getter ran: the generator's `POINTER_COUNTS` (`scripts/generator/config.mjs`) names it for every getter, and a getter without an entry stops the generator. `createPointerBuffer` and `readPointerStructs` refuse (`RangeError`) a count above the view's, so no count that JavaScript passes can read past the memory (`createPointerBuffer(view, 1e9, 1)` throws instead of faulting).
  - **Numbers and points** go through `createPointerBuffer(view, count, alignment)` (`cpp/runtime/PointerBuffers.*`): an external `ArrayBuffer` over Core memory whose `MutableBuffer` (`RetainedMemory`) holds a **duplicate of the owner's handle**, a reference of its own (`HandleObject::Duplicate`, which calls the `Retain` of the group). The memory is therefore valid for as long as the engine keeps the buffer even if the owner is disposed and the buffer is never touched again, and its destructor (any thread, during a collection) only releases that reference. **Mutable owners.** A reference keeps the Core object alive, not the array behind a pointer: a setter (`TRShapingEngineSetOpenTypeFeatures`) frees it while the object lives, and a kept pointer, length or buffer would read freed memory. `isHandleMutable(handle)` says whether Core lets the object change (a `TRMutable*` ref or any non-const ref type), and `CoreMemory` asks it on the first read: for a mutable owner it keeps nothing, and every read calls the `refresh` function that the wrapper passes to `coreNumbers`/`coreIndices`/`corePoints`/`coreStructs` (the getter and the count function again) and reads through that. A list over a mutable owner made without `refresh` fails on its first read. The list's `length` stays what it was when it was made; a read that finds fewer elements fails with a `RangeError`. The buffers a read makes are never kept. A mutable object must not be changed while a read runs (section 4). Debug hooks `testCreateMemoryProbe(bytes, mutable)` and `testReplaceMemoryProbe` free and replace the block (poisoning the old one with 0xDD) to test this, and the features of a real shaping engine are tested on a device. "Already disposed" does not come from the buffer: `CoreMemory` reads `owner.nativeHandle` before every read, and when it finds the owner disposed it also drops its cached buffer, so a disposed object is not kept alive by a list that nobody reads again. A list that is never read again after the owner is disposed (or never disposed at all) keeps the object alive until it is collected; that is the price of the retained reference.
  - **Read-only in practice.** An `ArrayBuffer` cannot be read-only (JSI has no such buffer), and the bytes are Core's `const` memory: the buffer is never given to app code by the library, and the count check keeps even a caller of the internal binding inside the array, but code that calls `createPointerBuffer` itself on a view it got from a getter can still write to those bytes. Closing that needs a copy instead of a view (O(n) per list), which was not chosen. Lists read it and `toTypedArray()`/`toFloat32Array()` return copies. Never pass such a buffer to a binding that fills a buffer in.
  - **Alignment.** A typed array checks its `byteOffset`, not the address, so `createPointerBuffer` takes the `BYTES_PER_ELEMENT` of the array that will read it as `alignment` and throws a `RangeError` when the address is not a multiple. Structs are never read through a typed array: `readPointerStructs(view, count, from, to)` copies each element out of Core memory into aligned storage and converts it with the codec of its element name (`FindStructCodec`), so TypeScript knows no offset and an unaligned struct is fine; it pins the owner with a duplicate for the whole call, since converting an element makes JavaScript objects and a setter could dispose the owner meanwhile. A name without a codec (`TRDrawCallbacks`, ...) is refused.
  - **TRUInteger is pointer-sized** (`uintptr_t`): the cluster map is 8 bytes an element on a 64-bit device and 4 on a 32-bit one, where Web's wasm32 always has 4. `coreIndices` reads it as `UInt32` in either width (little-endian: the low word; `TRInvalidIndex` reads as 4294967295 as on 32 bits), and `coreNumbers` refuses elements that are not as wide as the kind instead of reading them wrongly.
  - **Tests.** `tests/lists.test.ts` (node: logic, bounds, slices, laziness, disposal over a fake of the two native functions), `tests/device/ListTests.ts` (`runListTests(bindings, library, { fontBytes })`; debug hooks `testCreateMemoryProbe` and friends stand in for an object of Core that owns memory, so disposal, the finalizer path, the buffer's reference, release on another thread, alignment and forged views need no font; a real getter without a font (`TRFontFeaturesGetItemsPtr`) always runs, the shaping result glyphs run when the runner passes a font). The suite takes the library modules as an argument because Metro maps the `.js` suffix only for imports inside `src/`; the runner in `example/` has to import and pass them (not wired yet).
- Never convert Core data into arrays or objects in a constructor or cache it in a field: read when the property is asked for.

## 6. State the wrapper may keep

Only what Core cannot give back or must not be re-made on each read: the `Typeface` and the `OpenTypeFeature[]` set on a `ShapingEngine`, the frame and renderer a `LineLocator` was made with, the handlers in the callback table, and the platform image cache of a glyph image. Everything else is asked from Core each time.

## 7. Mapping rules (Core to TypeScript)

Same as the Web wrapper (`web-wrapper` skill, section 7) except where React Native differs:

| Core | Wrapper |
|------|---------|
| `index` + `length` parameters (never `TRRange`) | `fromIndex`/`toIndex`; the wrapper passes `index` and `toIndex - fromIndex`; order is validated in TypeScript, the upper bound is Core's |
| `TRInvalidIndex` / `NULL` | `-1` for an index, `undefined` for an optional object, `RangeError` for an invalid range, `Error` for a failed creation |
| `TRStringView` and text | UTF-16 (`TRStringEncodingUTF16`); indices are JS string indices |
| `TRColor` | `Color` = unsigned `0xAARRGGBB` number |
| `TRPath` | `Path` (verbs + coordinates) created from a native path; `toSvgPathData()` |
| `TRTag` | `SfntTag` = number, `SfntTag.make('head')` |
| Fonts | `FontFile.fromPath()`/`fromAsset()`/`fromBytes()`; no network fetch in the library |

Naming: classes PascalCase, members camelCase, no `I` prefix, no default exports, `T` prefix where Android and Cocoa have it (`TText`, `TMutableText`, `TLabel`, `TTextView`). Booleans read as `is…`/`has…`.

## 8. Text attributes

`TText` and `TMutableText` wrap `TRText`/`TRMutableText` with UTF-16. Attributes are one typed object, `TextAttributes = RunAttributes & ParagraphAttributes`, written by `TextAttributeCodec` with one `TRAttribute` per member. To support a new Core attribute: add it to the codec table with its kind, to `RunAttributes` or `ParagraphAttributes`, and a test that stores and reads it back. `userData` is a number (an application token). `Replacement` takes a `ReplacementDelegate { computeRoom(layoutWidth), draw?(context, bounds) }`.

**Built for #20 (node tests over a fake of Core's text; the device suite `example/tests/TextTests.ts` is written but has not run on a device).** `src/layout/TText.ts`, `TMutableText.ts`, `TextAttributes.ts`, `TextAttributeCodec.ts`. `TRTextSetAttribute` is bound by hand in `cpp/runtime/TextBindings.cpp` (declared in `NativeBindings.ts`); reading goes through `TRTextCopyAttributes`, `TRAttributeListGetItem` and `readPointerStructs("TRAttribute")`. Ranges are checked in TypeScript (`RangeError`), an empty range is a no-op, and `setAttributes` prepares and checks every member before it sets the first: invalid arguments are refused before the first is set (a failure inside Core can still leave earlier members set). Counts and tokens are bounded to 32 bits, floats to `FLT_MAX`, `textAlignment` to the `TextAlignment` values. Core retains a typeface or font features it is given: a temporary `FontFeatures` made from an array is disposed after the call. A read gives wrappers (`typeface`, `fontFeatures`) that the reader owns and disposes. `TMutableText.append`/`insert` of an empty string are no-ops in TypeScript because Core refuses a `NULL` buffer there. `replacement` (`TRAttributeReplacement`, added with #21) takes a `Replacement` wrapper; a read gives a wrapper that the reader owns and disposes, and a type that has no member gives its reference back.

**Built for #21 (node tests over a fake of Core's layout objects in `tests/layout.test.ts`; the device suite `example/tests/LayoutTests.ts` is written but has not run on a device).** `src/layout/` has `Typesetter`, `FrameResolver`, `ComposedFrame`, `ComposedLine`, `GlyphRun`, `LineLocator`, `Replacement` (and `Checks.ts`, the argument checks they share); `src/drawing/ReplacementDelegate.ts` has `ReplacementDelegate { computeRoom(layoutWidth), draw?(context, bounds) }`, `ReplacementRoom` and `ReplacementBounds`. `TRTypesetterCreate` is bound by hand next to `TRTextSetAttribute` (`cpp/runtime/TextBindings.cpp`: an array of `{ type, value }` attributes, the text handle converted last, `RethrowCallbackError(rt, result)` after the call). Rules that were settled there: `ComposedFrame`, `ComposedLine` and `GlyphRun` are made only by their parent (a `Get` binding already retains, so `adopting`), and every read of `frame.lines`, `line.runs`, `run.typeface`, `run.replacement` or `resolver.typesetter` is a wrapper that the reader disposes; a child never needs its parent, so the order of disposal does not matter; the glyph lists of a run are lazy `coreNumbers`/`corePoints`/`coreIndices` over the run, which is immutable. Ranges are `fromIndex`/`toIndex`, checked in TypeScript for order, sign and (where Core says MUST NOT be zero) emptiness; Core's `NULL`, `-1` and `TRFalse` for a range outside the text are `RangeError`, except `getLineIndexForCodeUnit`, `getClusterStart/End` and `getFirstLineIndexBelow`, which keep `-1`. A NaN is a `RangeError` for every float (the marshalling refuses it, though Core defines NaN for some), and an infinite one is valid. `FrameResolver.maxLines` is `undefined` (or 0) for no limit and refuses a negative count. `Replacement` keeps nothing in the wrapper: the handler (`{ computeRoom, draw? }`, which calls the delegate as itself) lives in the handler table until Core finalizes the replacement, so a text attribute, a typesetter and the runs of a frame keep the delegate after the wrapper is disposed, and there is no `delegate` getter (Core cannot give the key back). `LineLocator` keeps a reference of its own to the frame and the renderer (taken with `TRComposedFrameRetain`/`TRRendererRetain`, released by its `dispose()`), so disposing what it was made with does not hurt it. The scenario matrix (`example/tests/layoutScenarios.ts`) is run against Tehreer-Web's WebAssembly build to make `layoutExpected.ts`; regenerate it by running `measure` and `measureTypesetter` with the Web library and the fonts of Core. The calls that can reach a `computeRoom` (the typesetter constructor and line makers, `FrameResolver.createFrame`, `Replacement.computeRoom`) run through `holding` (`src/internal/Holding.ts`, native `retainHandle`), which gives them references of their own to the receiver and the other objects they use for the length of the Core call, so a handler that disposes a wrapper takes effect when the call returns (device test D1); the buffer of a truncation token is still the known limit above. What `computeRoom` returns is checked in `Replacement.ts`: not an object of three numbers is a `TypeError`, a NaN, negative or too big number a `RangeError` (the shared marshalling elsewhere throws a plain `Error` for a float that is not a number). Core does not clamp a justification factor or level, and the wrapper does not either. Core refuses a typesetter whose replacement range has no typeface (ShapeResolver.c), though TRTypesetter.h says it is not needed: the text or the defaults must give every range a typeface. `GlyphRun.isBackward` is Core's "the run opposes the default direction of its script", false for right-to-left Urdu.

## 9. Drawing and views

Core draws; the wrapper provides primitives.

- **Draw callbacks.** The views call `TRGlyphRunDraw`, `TRComposedLineDraw`, `TRComposedFrameDraw` with `TRDrawCallbacks` implemented **natively** by the platform painter (Android `Canvas`, iOS `CGContext`; issues #24 and #25). Drawing never round-trips glyph by glyph through JS in the view path. `GlyphRun.draw`, `ComposedLine.draw` and `ComposedFrame.draw` (`draw(renderer, context, x, y)`, as Tehreer-Web) are the **JS-visible drawing surface, the slow path**: one JS call for every glyph image, rectangle and shadow, meant for custom surfaces and tests. The native painters implement the same callbacks and must produce the same calls, so the recording `DrawingContext` of the device suite is their reference.
  - **Built for #22 (node tests over a fake of Core's draw functions in `tests/drawing.test.ts`; the device suite `example/tests/DrawingTests.ts` is written but has not run on a device).** `src/drawing/DrawingContext.ts` is an interface, not Web's canvas type: `drawGlyphImage(image, x, y, scaleX, scaleY, color, clip)`, `fillRect(rect, color)` (both required) and `beginShadow`/`endShadow` (optional; Core opens a scope only if both are set, so with one of them neither is installed). `drawGlyphPath` (outlines) is not exposed: with `drawGlyphImage` set Core passes images anyway, and the Web wrapper has no outlines either. `drawReplacement` is not a member of the context: the replacement's own `ReplacementDelegate.draw(context, bounds)` is called with the context (`bounds` in pixels, run metrics times the render scale, as Web).
  - **Install and restore (`cpp/runtime/DrawBindings.cpp`, hand-written; `TRRendererSetDrawCallbacks` stays in `MANUAL`).** `Drawing.ts` (`drawIntoContext`) validates the context, takes references of its own to the receiver and the renderer (`holding`), calls `installDrawContext(renderer, adapter)`, runs the generated `TRGlyphRunDraw`/`TRComposedLineDraw`/`TRComposedFrameDraw`, and calls `restoreDrawContext(scope)` in a `finally`. Install puts the handler (the adapter, a plain object made around the context) in the handler table, sets the static trampolines (`InvokeHandler`, `noexcept`, errors recorded and rethrown by the generated draw binding, so the first error of a member is the one thrown and no member is called after it). **Shadow pairing:** this includes `endShadow`: if a member throws inside a shadow scope, `endShadow` is not called (Core stops at the first error, as for every callback); a context that keeps state between the two must reset it when the draw throws and returns a `DrawScope` host object that remembers the renderer's previous callbacks and user data (it holds a renderer reference). Restore puts them back (a native painter's included, also after an error), removes the handler and drains the queue; a scope that is garbage collected unrestored only gives its reference and key back and never touches the callbacks (not thread safe). A nested draw into the same renderer restores the outer context's callbacks. Nothing is kept after the call, unlike `TRReplacementCreate`.
  - **Ownership of what the callbacks lend.** The image and the run that Core passes are borrowed for the call. The trampoline wraps each in a new handle with a reference of its own (`Ownership::Retain`), the adapter makes a `GlyphImage` of it and disposes it (and the run handle) in a `finally` after the member returns, so a wrapper that a member keeps is "already disposed" afterwards and no reference leaks on any path; a handle nobody disposed is released by its finalizer. A member that wants to keep a picture copies `pixels` or builds its own image inside the call. Images are shared with the glyph cache, so a surface caches what it makes from the pixels, not by the wrapper.
  - **Replacement draw hook.** Core cannot give the `userData` of a replacement back, so `ReplacementBindings.cpp` keeps a process-wide `KeyRegistry` (replacement pointer to handler key, erased in `Finalize`), and `invokeReplacementDraw(replacement, context, bounds)` finds the handler of a replacement that a run reports and calls its `draw`. The adapter's `drawReplacement` gets the replacement from the run (`TRGlyphRunGetReplacement`, a retaining `Get`), calls `Replacement.draw` (internal) and disposes both handles. It returns false when the delegate has no `draw` (nothing is drawn).
  - The debug hooks `testSetNativeDrawCallbacks(renderer, isSet)` (a native painter stand-in with its own user data) and `testGetDrawCallbacks(renderer)` (which callbacks are set) let the device suite check that a renderer's callbacks are back after a draw or an error.
- **Origins and scale** follow Core (run: start on its baseline; line: origin of its container; frame: top left). Core multiplies positions by `renderScale`; the platform transform applies after.
- **Fabric views (built for #26; iOS and Android results are in the PR).** `TLabel` and `TTextView` are Fabric components with a **hand-written C++ shadow node** that measures through Core. The base is `TehreerTextBase` (`cpp/fabric/`, spec `src/specs/TehreerTextBaseNativeComponent.ts`, wrapper `src/views/TextBase.tsx`, iOS `ios/TehreerTextBaseView.mm`, Android `TehreerTextBaseManager.kt`); it paints the frame its shadow node composed (#24, #25).
  - **Measurement.** `TehreerTextBaseShadowNode` has the traits `LeafYogaNode` and `MeasurableYogaNode` and overrides `measureContent`: it decodes the `text` prop (UTF-8 on the wire, back to UTF-16 in `Utf8.h`), calls `tehreer::fabric::ComposeFrame` (`TextFrameComposer.cpp`: `TRTextCreate`, `TRTypesetterCreate` with the typeface and size as defaults, `TRFrameResolver` with the Yoga maximum as frame size, `fitsHorizontally` and `fitsVertically`, `maxLines`, `TRFrameResolverCreateFrame`) and returns the frame's width and height, clamped to the constraints. Same calls and numbers as the JS `Typesetter`/`FrameResolver`; no JS is involved. Yoga rounds a measured size up to the pixel grid, and the rounding of the node's position adds to that, so the laid-out size is the frame bounds plus up to two pixels (the device suite allows `2 / PixelRatio + 0.01` above and 0.01 below); the frame in the state is composed for the box with a 0.01 slack on both sides. A fixed `width` style is not measured (use `maxWidth` and `alignSelf`).
  - **State handoff.** `layout()` composes the frame again for the box Yoga chose (`fitsHorizontally` off, so the alignment of the lines holds inside the box) and calls `setStateData` only if the key (text, tag, size, max lines, box) changed. The state data holds a `shared_ptr<const ComposedFrameBox>` (one `TRComposedFrame` reference, released by the last owner on any thread). iOS: the view keeps `_state` and reads `getData().frame`. Android: `RN_SERIALIZABLE_STATE` is defined, so the state data must have `getDynamic()` and a constructor from `folly::dynamic`; the Kotlin view reads `getMapBuffer()` (status, line count, bounds, box) without JNI. The Android state map buffer also carries the **id of the frame** (key 6, `ComposedFrameBox::id()`); `FrameRegistry` (`cpp/fabric`) maps an id to a `weak_ptr` (the box removes itself in its destructor), and the painter's JNI `setFrame` takes a share of the frame by id, so nothing hands out a raw pointer.
  - **Typeface.** Referenced by `typefaceTag` from Core's process-wide `TRTypefaceManager`. The composer looks it up with `TRTypefaceManagerEnumerateTypefaces` and retains inside the callback, not with `TRTypefaceManagerGetTypeface`, whose result is not retained and can die on unregister between the call and a retain. The typeface must be registered **before the component is mounted** and stay registered while it is shown: the lookup happens at measurement, and registering later re-measures nothing until a prop changes. An unknown tag, empty text or a non-positive size composes nothing: the node measures 0 by 0 and the state has no frame. Nothing is thrown (Yoga cannot receive an error).
  - **Replacements in the measure path (#29).** Yoga measures on whichever thread commits, and a JavaScript `computeRoom` runs only on the thread of the runtime (section 4), so Core would get a room of zero from it without an error. The native side therefore refuses text that holds one: `registerViewText` returns 0 and `ComposeFrame` reports `ForeignReplacement`. `src/views/ViewText.ts` makes every replacement static first: it asks the delegate for its room (with the width the view reported through `onLayout`, 0 before) and records its `draw` as filled rectangles (`fillRect` only; `drawGlyphImage` throws), and `createStaticReplacement` gives Core a replacement whose callbacks are plain data (`cpp/fabric/StaticReplacements.*`, freed by Core's `finalize` with the last reference). The painter's `ReplacementTarget` fills those rectangles at the run's origin; nothing runs JavaScript while painting. The room is a snapshot: when a delegate's room depends on the width, the view asks again on `onLayout` and makes the text again only if a room changed.
  - **Attributed text (#27).** The shadow node only receives props, so `ViewText` registers an immutable copy of the `TText` under an id (`cpp/fabric/ViewText.*`, `ViewTextRegistry`, ids never reused) together with the default typeface and size, and the `textId` prop carries it; no typeface tag and no `TypefaceManager` registration is needed on this path (the plain `text`/`typefaceTag` path of #26 stays). The component's props are Core's settings (`textAlignment`, `truncation*`, `maxLines`, `extraLineSpacing`, `lineHeightMultiplier`, `justification*` set the `TRFrameResolver` as they are). `shouldNewRevisionDirtyMeasurement` compares only the props that lay out text, so color, selection and scroll requests never measure or compose again. A replaced `ViewText` is released 250 ms after the commit, because the previous revision may still be measuring it on another thread.
  - **TTextView (#28).** The same component with `scrollable`: the frame is composed once for the width with an unbounded height (re-composed only when the key changes), the native view scrolls (iOS `UIScrollView` with a screen-sized canvas moved on every scroll; Android `OverScroller` and `scrollTo` on the view) and `FramePainter` paints with `FramePaint::isWindowed`: the lines whose boxes meet the visible rectangle come from a `TRLineLocator` (kept per painter and frame, with a frame reference), so a scroll lays nothing out and touches only the lines in view. Selection (`selectionStart/End/Color`) is filled with `TRComposedFrameEnumerateSelection` before the text. Hit testing, selection rectangles and carets are TypeScript over the very frame that is painted: `onFrameReady` carries `frameId`, `acquireViewFrame` hands out a reference (`FrameRegistry`, now registered on both platforms), and `src/views/FrameQueries.ts` calls `getLineIndexAtPosition`, `getCodeUnitIndexAtDistance` and `getCodeUnitDistance` of Core. Taps are native events (`onTextTap`, in text coordinates with the scroll offset added) turned into indices in JavaScript; scrolling is requested with `scrollToOffset` plus a token prop.
  - **Limits of #27 to #29.** Links (`userData` taps) and highlights lists are not implemented (one selection range is); a replacement in a view can only fill rectangles; its room is not recomputed during native layout; the text is read when the `attributedText` prop changes identity.
  - **Registration (verified on RN 0.88.0).** Codegen: `codegenConfig.type` is `all` (with `modules` the component spec is ignored), the spec file name ends in `NativeComponent.ts` and passes `{ interfaceOnly: true }`, which makes codegen write Props, EventEmitters and the Java interface but no ShadowNode, State or ComponentDescriptor. iOS: `codegenConfig.ios.components.<Name>.className` maps the name to the `RCTViewComponentView` subclass (generated `RCTThirdPartyComponentsProvider`), and that class returns `concreteComponentDescriptorProvider<TehreerTextBaseComponentDescriptor>()` from `+componentDescriptorProvider`. Android: `react-native.config.cjs` lists `componentDescriptors: ["TehreerTextBaseComponentDescriptor"]`, which makes the Gradle plugin add `providerRegistry->add(concreteComponentDescriptorProvider<...>())` to `autolinking.cpp` (the CLI scans the specs for this itself, but skips an `interfaceOnly` component, so without the entry nothing is registered and no error is shown: the app starts, and the view is a plain 0 by 0 node that never measures). The generated `autolinking.cpp` includes only the codegen `ComponentDescriptors.h` (empty for `interfaceOnly`) and `TehreerModule.h` (`cxxModuleHeaderName`), so `TehreerModule.h` includes the hand-written descriptor header. `TehreerPackage.createViewManagers` returns the Kotlin manager; `android/CMakeLists.txt` globs `cpp/fabric/*.cpp`. **The CMake target must call `target_compile_reactnative_options` (with `-Wno-error` after it):** without `RN_SERIALIZABLE_STATE` the target builds a different `ConcreteState` than React Native's (an ODR mismatch that compiles and links), and on the emulator every node measured 0 by 0 and no state reached Kotlin. Linking `react_codegen_TehreerSpec` does not pass the definitions on.
  - **Events.** `onFrameReady` (`lineCount`, `width`, `height`) is sent by the native view from `updateState`, read from the state: iOS through the generated event emitter, Android with a `topFrameReady` `Event` (`canCoalesce` false). The device suite uses it as the evidence that the view received the frame.
  - **Not done / limits.** Font scaling and `layoutDirection` are ignored; padding and borders are not applied (the frame is painted at the origin of the view); a typeface must stay registered while the component is shown.
  - **Native painters (built for #24 and #25; Android results: device suite and screenshots in the PR).** `cpp/painter/` is shared: `PaintTarget` (the primitives a platform provides: `DrawGlyphImage`, `FillRect`, `BeginShadow`, `EndShadow`, `DrawReplacement`), `PaintCallbacks` (noexcept `TRDrawCallbacks` that forward to a target through `userData`, `DrawFrame` which installs them on a renderer for one call and puts the previous callbacks back, and `FramePainter`, the renderer of a view), `PaintCounters` and `OffscreenSurface` (a platform function used by the tests). Platform code: `android/src/main/cpp/` (`CanvasPainter`, JNI to `android.graphics.Canvas`; `TextBaseJni.cpp`; `OffscreenSurface.cpp`; the Kotlin side is `TehreerPaintJni` and `TehreerTextBaseView.onDraw`) and `ios/` (`TehreerCoreGraphicsPainter`, `TehreerOffscreenSurface.mm`, `TehreerTextBaseView.drawRect:`).
    - **Units.** A view's frame is in layout units and the renderer's render scale is the display density, so Core's images are in device pixels. Android: the view canvas is in pixels, nothing is scaled. iOS: the painter scales the context by `1 / density` (the context is UIKit's, y down, in points). The platform transform therefore applies after Core's scale, and the frame is drawn with its top left at the view's origin.
    - **Images.** Cached on the glyph image with `GetOrAttachNativeData` and destroyed by Core (any thread: Android attaches the thread to drop the global reference to the `Bitmap`; iOS releases the `CGLayer`). Alpha: Android `ALPHA_8` tinted by the paint color, iOS an image mask in a `CGLayer` drawn with the fill color. ARGB is **premultiplied** in Core (the issue text says "unpremultiplied"; Core's header is the authority): Android repacks A,R,G,B to R,G,B,A in a premultiplied `ARGB_8888` bitmap and draws with an opaque white paint (the foreground color does not tint a color glyph); iOS uses a premultiplied-first, big-endian `CGImage`. The scale of a bitmap-font strike is applied to the destination rectangle. A clip is `save`/`clipRect`/`restore` (`CGContextClipToRect`).
    - **Shadow.** One scope draws into a layer and is composited at `EndShadow`, as Core recommends (a glyph that is filled and stroked casts one shadow). Android: a layer `Bitmap` the size of the canvas clip, blurred with `extractAlpha` and a `BlurMaskFilter`, drawn at the offset, then the layer on top (`Paint.setShadowLayer` does not shadow bitmaps and is not supported on a hardware canvas). Assumes a canvas whose local unit is a pixel: the view canvas has no scale or rotation of its own (documented on `CanvasPainter`, not asserted: reading the matrix costs a JNI object per scope). Shadow scopes are counted, so a nested Begin/End pair does not close the outer scope. Every shadow scope gets a fresh layer bitmap (a hardware canvas records the composite and rasterizes later), dropped at `EndShadow`; a failure in the blur only costs the shadow, the scope's content is always composited. Cached glyph bitmaps and the layer are not `recycle()`d (a hardware canvas may still read them); the global reference is dropped and the garbage collector frees them. If the layer cannot be made the scope is drawn without a shadow. iOS: a transparency layer with `CGContextSetShadowWithColor`; its offset and blur are in the context's base space (points), so they are divided by the density.
    - **Replacements.** A `ReplacementDelegate.draw` is JavaScript that cannot run on the UI thread, so the platform painters' `DrawReplacement` draws nothing by default; the views wrap their target in `ReplacementTarget` (`cpp/painter/PaintCallbacks.cpp`), which fills the rectangles of a static replacement (#29). The test hook `testPaintFrame` gives a JS function the run and a drawing context whose primitives are the painter's, which is how the delegate's `draw` is covered on the JS-visible path.
    - **Tests.** `example/tests/PainterTests.ts` (suite `painters`) draws the scenes of `paintFixtures.ts` with the debug hook `testPaintFrame` on the platform canvas and compares the pixels with the callbacks of the same frame composited in TypeScript; shadow position (both densities), render scale, bitmap counts (`testGetPaintCounts`) and error paths have their own tests. The visual check is the "Show frames" button of the example app (`VisualCheck.tsx`; debug builds only): the Fabric view plus every scene as a PNG made by the same painter. QA screenshots it on both platforms.
    - **Not verified.** The shadow of the Android *view* (a hardware canvas) is not drawn by any scene (the view's renderer has no shadow); the Android offscreen canvas is a software one. 32-bit ABIs and API levels other than 30 were not run.
- **Glyph images.** Alpha images are tinted per color, ARGB images are unpremultiplied (iOS) or drawn with the right alpha mode (Android); cache the platform bitmap on the glyph image through `TRGlyphImageSetNativeData` and destroy it in the destroy callback.
  - **Built for #18.** `Renderer`, `GlyphCache` and `GlyphImage` (`src/graphics`) bind everything of `TRRenderer.h`, `TRGlyphCache.h` and `TRGlyphImage.h` except the draw callbacks (`TRRendererGet/SetDrawCallbacks`, `TRRendererGetDrawUserData`: native painters set them; `GlyphRun.draw` and its siblings set them for the length of one call, #22) and the native data (`TRGlyphImageGet/SetNativeData`: native only). Painters use `cpp/runtime/GlyphImageNativeData.h` (`GetOrAttachNativeData`, with the rules of Core for the race, the destroy thread and sharing through the cache); debug builds have `testAttachNativeData`, `testGetNativeDataSerial` and `testGetNativeDataCounts` (`cpp/runtime/GlyphImageTestHooks.cpp`) to test it without a painter. Renderer settings are never mirrored. A glyph cache capacity of -1 is refused in TypeScript, since the binding would read it as `TRInvalidIndex`.

## 10. Updating the wrapper after a Core change

1. **Identify the change.** `git diff <old>..<new> -- Headers/Tehreer` in the submodule. Read the Doxygen of every changed function: ownership, range semantics, out parameters, `stop`.
2. **Bump the submodule** with `scripts/sync-core` (fetch the SHA, check it out, stage the pointer). Unpushed Core commits are fetched with `git fetch /Users/mta/Learning/Tehreer-Core main` inside the submodule.
3. **Regenerate** bindings (`node scripts/generate-bindings.mjs`). A removed or renamed function shows as a type error in TypeScript and a compile error in C++; a new one as a new member of `NativeFunctions`.
4. **Fix call sites,** then structs (`static_assert`s fail until the C++ description agrees with the header).
5. **Adopt, don't just port.** Delete wrapper logic that Core now owns. Add members for new capabilities with the names of section 7 and a test. Keep Web, Android and Cocoa in step.
6. **Test** (section 11), update `README.md` if a convention or limitation changed.
7. **Commit** only when asked: tag `[lib]`, `[test]`, `[native]`, `[ios]`, `[android]`, `[ci]` or `[docs]`, imperative summary; stage files explicitly.

## 12. Gotchas

- Do not hold a raw pointer from Core (a buffer from a `*Ptr()` getter) across a call that can free its owner; keep the owner alive with the list or view that exposes it (a `PointerView` alone does not keep the Core object alive, only its handle wrapper; `createPointerBuffer` and `readPointerStructs` take a reference of their own). A reference does not keep the array alive for a **mutable** owner (a setter frees it): never cache a pointer, a length or a buffer of one, ask the getter and the count function again (section 5).
- `TRUInteger` is `uintptr_t`: 8 bytes on 64-bit devices. Never read a buffer of `TRUInteger` (the cluster map) as `Uint32Array`; use `coreIndices`.
- A float that Core returns arrives as a double of a 32-bit float; compare with a tolerance in tests.
- Unsigned results (`TRColor`, `TRTag`) must be converted with `>>> 0` when they pass through a signed 32-bit value.
- `TRVersionGetString` is declared but never implemented; use the `TEHREER_VERSION_STRING` macro.
- SFNT tags may contain a space (`URD `).
- Core objects freed from a finalizer may run on a non-JS thread: finalizers only call `TR*Release` (thread safe) and never touch JS.
- iOS pod: Core and SheenBidi both have a `Source/Core/` with headers of the same names, so each needs its own Source folder as a per-subspec `-I` flag, never in the shared `HEADER_SEARCH_PATHS`. Core ships `Headers/Tehreer/module.modulemap`; with clang modules on, SheenBidi's names become ambiguous, so the pod sets `CLANG_ENABLE_MODULES = NO`. C files need a per-subspec `-std` (Core `c89`, dependencies `gnu99`; verified in the build log), and `harfbuzz.cc` must be in a subspec with no `-std` flag (clang rejects it for C++). `pod install` needs `LANG=en_US.UTF-8`.
- Android: the NDK has no libbz2, so FreeType's optional libraries are disabled; `ndkVersion` in `example/android/build.gradle` must name an installed NDK (the template's 27.1 is not).
- Android: C++ standard library and `-fvisibility` settings must match Core's unity build; iOS: Core is compiled as C89 inside an Objective-C++ target, so compile the C files with the C language setting, not as C++.
- Do not change the typeface of a renderer, the settings of a shaping engine, or a mutable text while something is drawing or shaping with it.
